## 1. Target topology (unchanged, ARCHITECTURE.md §8)

Browser → Cloudflare Pages (static React build) and → Caddy (TLS) → Spring Boot API container on one
VPS (Docker Compose) → Supabase PostgreSQL. Supabase Auth issues tokens; the API verifies them with
the public JWKS. No Kubernetes, brokers or extra services.

## 3. Health, readiness and the container

- `GET /actuator/health/liveness` — process alive (does **not** depend on the DB, so a DB outage
  does not restart-loop the API).
- `GET /actuator/health/readiness` — started **and** DB reachable; used by the image `HEALTHCHECK`
  and by Caddy's active health check.
- `GET /api/v1/health` — public, for external uptime monitors (Caddy hides `/actuator/*`).
- Image: non-root `app` user, JRE only, `-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError`.
- `deploy/compose.prod.yaml`: API not published on the host (only Caddy reaches it), `mem_limit 1g`,
  `cpus 1.5`, `pids_limit 512`, read-only root FS with tmpfs `/tmp`, `no-new-privileges`, JSON log
  rotation (5 × 10 MB), `stop_grace_period 40s` (graceful HTTP shutdown 20 s + AI grace 10 s).

`server.forward-headers-strategy=native` makes Tomcat honour `X-Forwarded-*` **only** from
private-network peers (Caddy on the Docker network); the API port must not be published. Rate limits
never use client addresses (they are per account).

**Staging**: use the same `prod` profile with a separate Supabase project, separate database, its own
domain and origins (`CORS_ALLOWED_ORIGINS`, Supabase redirect URLs), and `LEGAL_*` versions equal to
production. 🟡 No staging environment exists yet.

## 5. Supabase production settings (🛠 manual)

### 5.1 Authentication
- **Confirm email: ON** (required — without it sign-up reveals registered addresses and unverified
  addresses can play).
- Password policy: minimum length ≥ 8 (the frontend checks 8), leaked-password protection if the
  plan offers it.
- JWT Signing Keys: asymmetric (ES256/RS256) — HS256 is rejected by the API. JWT expiry: keep the
  default 3600 s or shorter.
- Refresh tokens: rotation on, reuse interval ≤ 10 s; consider an inactivity timeout / time-box.
- Rate limits (Authentication → Rate Limits): keep the defaults for sign-up, sign-in, token
  refresh, OTP/verification and emails per hour, or lower them.
- **CAPTCHA protection: ON**, provider Cloudflare Turnstile, with the widget's secret key (Cloudflare
  dashboard → Turnstile → add the frontend domain). Build the frontend with the matching
  `VITE_TURNSTILE_SITE_KEY`; enable both in the same release.
- Anonymous sign-ins: **off** (the API rejects anonymous tokens anyway).
- Secure password change: may be enabled; the account page re-authenticates before changing.

### 5.2 URLs
- **Site URL**: `https://<frontend-domain>`.
- **Redirect URLs** (allow-list exactly these, no wildcards in production):
  `https://<frontend-domain>/login` (email confirmation) and
  `https://<frontend-domain>/reset-password` (password recovery). For local development:
  `http://localhost:5173/login`, `http://localhost:5173/reset-password`.
- Email templates use `{{ .ConfirmationURL }}` (default); the links land on the routes above, which
  handle expired or reused links ("request a new one").

### 5.3 SMTP
Supabase's built-in email sender is for development only (very low hourly limit, no deliverability
guarantees). Production needs a **custom SMTP provider** (Authentication → SMTP settings):
host, port, username, password, sender address and name; SPF, DKIM and DMARC records on the sender
domain; a verified sender. Raise the email rate limit only after SMTP is configured. Test both emails
(confirmation, recovery) end to end in staging. 🛠 Provider choice and DNS are operator decisions.

### 5.4 Deleted accounts
The API anonymizes the game account at once and refuses its tokens; the **Supabase Auth user
(email, password hash) must be deleted by the operator**:
```sql
SELECT supabase_user_id, deleted_at FROM game.player WHERE deleted_at IS NOT NULL ORDER BY deleted_at;
```
Delete each in Supabase → Authentication → Users (or with the Admin API from an operator machine —
never from the app or the frontend). The deadline is an operator decision (Privacy Policy §5).

### 5.5 Database roles
Application role `strategy_app`: `USAGE` on schema `game`, DML on its tables and sequences, no DDL,
**`BYPASSRLS`**. Migration role `strategy_migrator`: owner of schema `game`. Backup role
`strategy_backup`: read-only (`SELECT`), `BYPASSRLS`. Every table has RLS enabled with no policies
(V23), so a role without `BYPASSRLS` that does not own the tables sees no rows. Script:
`deploy/supabase/app-role.sql` (step 1 before the first start, step 2 after it). 🟡 Not yet run
against a real Supabase project. The `game` schema must not be exposed through the Supabase Data API.

## 6. Reverse proxy, HTTPS and headers

`deploy/Caddyfile`: automatic TLS for `$API_DOMAIN`, HSTS, `nosniff`, `Referrer-Policy`, removes
`Server`, 256 KB body cap at the edge, `/actuator/*` → 404, active health checks, access logs
commented out until an IP-log retention period is decided. The API adds its own CSP
(`default-src 'none'`), `X-Frame-Options: DENY`, `Cache-Control: no-store`.

Frontend (Cloudflare Pages): `npm run build` writes `dist/_headers` (CSP, HSTS, `nosniff`,
`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) from `VITE_API_BASE_URL`,
`VITE_SUPABASE_URL` and `VITE_TURNSTILE_SITE_KEY` (`frontend/securityHeaders.ts`); a build without
the two origins writes none and warns. 🟡 Verify in staging that sign-in, the API, and the optional
3D map work under the CSP (check the browser console for violations).

## 7. Database migrations (Flyway)

- Migrations run on application start (`spring.flyway`), `clean` disabled, validation on.
- Rules: never edit an applied migration; every change is a new `V<n>__*.sql`; **expand/contract**
  (add columns nullable or with defaults, backfill, switch code, drop later) so the previous image
  still runs against the new schema — that is what makes image rollback safe.
- V20 (Phase 15A) only adds nullable columns, a table and an index: the Phase 13 image runs against it.
- Before a release: take a backup (§8), then deploy. A failed migration aborts start-up and leaves
  the previous container running if you deploy start-first.

## 8. Backup and restore

- **First line**: Supabase's managed backups (daily on paid plans; point-in-time recovery as an
  add-on; none on the free plan). They also cover Supabase Auth (emails, password hashes). Our own
  copy covers Auth only with `BACKUP_INCLUDE_AUTH=true` (below); without either, losing the Supabase
  project means players re-register and their new accounts no longer match their games.
- **Independent copy** (`deploy/backup/`, image `strategy-backup`: pg_dump 17, GnuPG, rclone, curl):
  - **Nightly at 03:45 UTC** (`systemd/strategy-backup.timer`): `backup.sh` dumps schema `game` (and
    Supabase's `auth` schema into the same file when `BACKUP_INCLUDE_AUTH=true`, which needs step 3 of
    `deploy/supabase/app-role.sql`) with the read-only role `strategy_backup`, checks the dump with `pg_restore --list` and encrypts it to a
    GnuPG **public** key before it reaches the disk. The plaintext exists only inside the container.
    The private key is never on the server, so neither the server nor the storage provider can read a
    backup.
  - **Offsite**: `offsite.sh` copies each new file to a Backblaze B2 bucket (EU region) and marks it
    offsite only after rclone has compared size and checksum. Existing objects are never replaced. The
    B2 key is restricted to the bucket and has **no `deleteFiles`** capability, so a compromised server
    cannot wipe the backups.
  - **Hourly** (`systemd/strategy-backup-offsite.timer`): `offsite.sh` retries failed uploads, removes
    local copies older than 30 days that are confirmed offsite (never the newest), and **alerts** when
    the newest offsite copy is older than 26 hours (catches failed backups and failed uploads): exit
    status 1, log line `ALERT: …`, and `<heartbeat-url>/fail` when `BACKUP_HEARTBEAT_URL` is set
    (healthchecks.io or Better Stack heartbeat: period 1 h, grace 1 h; a missing ping also alerts).
  - **Offsite retention**: a B2 lifecycle rule on the bucket hides files 30 days after upload and
    deletes them a day later. 30 days is the period in the Privacy Policy (§5).
- **Restore**: download the `.dump.gpg` (B2 web UI or rclone), decrypt it on the machine that holds the
  private key (`gpg --output x.dump --decrypt x.dump.gpg`), then
  `deploy/backup/restore.sh <dump> <expected-database-name>` (refuses encrypted files and a mismatching
  target, drops and restores schema `game` in one transaction, prints row counts). It restores only
  `game`, also from dumps that carry `auth`, so it never touches the target's accounts.
- **Restoring accounts** (only after losing the Supabase project; 🟡 not rehearsed against Supabase):
  in the new project, before anyone signs up, load the `auth` rows from the same decrypted dump with
  `pg_restore --schema=auth --data-only --disable-triggers --no-owner --dbname=<new project URL> <dump>`
  as the project's `postgres` role, then restore `game` with `restore.sh`. Supabase does not officially
  support moving `auth` between projects, so rehearse this once on a scratch project and record what
  was needed.

### 8.1 Setting it up (🛠 at deployment)

1. **Key pair, on your own computer** (Gpg4win on Windows), never on the server:
   ```
   gpg --quick-generate-key "Blaspi backups" default default never
   gpg --armor --export "Blaspi backups" > backup-public.asc
   gpg --armor --export-secret-keys "Blaspi backups" > backup-private.asc
   ```
   Store `backup-private.asc` and its passphrase in your password manager (and one more place you
   control), then delete the file. **Without it no backup can be restored.**
2. **Backblaze B2**: a private bucket in the EU region; lifecycle rule
   `{"fileNamePrefix": "", "daysFromUploadingToHiding": 30, "daysFromHidingToDeleting": 1}`; an
   application key restricted to that bucket with `listBuckets, listFiles, writeFiles` (add
   `readFiles` only if rclone asks for it; the files are encrypted). Optionally enable Object Lock.
3. **Database role**: `strategy_backup` from `deploy/supabase/app-role.sql`.
4. **On the VPS**:
   ```
   docker build -t strategy-backup deploy/backup
   install -d -o 70 -g 70 -m 700 /srv/strategy/backups      # uid 70 = postgres in the image
   install -d -m 700 /etc/strategy
   cp backup-public.asc /etc/strategy/ && chmod 644 /etc/strategy/backup-public.asc
   cp deploy/backup/backup.env.example /etc/strategy/backup.env && chmod 600 /etc/strategy/backup.env
   cp deploy/backup/systemd/* /etc/systemd/system/
   systemctl daemon-reload && systemctl enable --now strategy-backup.timer strategy-backup-offsite.timer
   systemctl start strategy-backup.service && journalctl -u strategy-backup -n 50
   ```
   The units use the host network because Supabase's direct database host is IPv6-only without the
   IPv4 add-on (otherwise use the session pooler URL, see `backup.env.example`).
5. **Monthly restore drill**: download the newest backup, decrypt it, restore it into an empty scratch
   PostgreSQL 17 (`docker run -d -e POSTGRES_PASSWORD=… postgres:17-alpine`), compare the row counts
   with production and note the time taken.

🧪 **What was verified (2026-11-03, locally only):** the `strategy-backup` image against scratch
PostgreSQL 17 containers, with a local folder in place of B2: the backup file is encrypted (no
plaintext in it) and its SHA-256 matches; it is marked offsite only after the check; an upload into
an unwritable destination fails, is retried on the next run and then succeeds; an existing remote
object with different content is not replaced and the copy stays unconfirmed; local copies older
than 30 days are removed only when confirmed offsite; a 1504-hour-old or missing offsite copy raises
the alert; a backup decrypted with the private key restored into a second database with the expected
row counts and Flyway version 23; `restore.sh` refuses an encrypted file. Earlier (2026-10-22): a
restore of all 59 tables with identical row counts, and the `prod` jar starting against the restored
copy.

🧪 **2026-11-09, locally:** with `BACKUP_INCLUDE_AUTH=true` the encrypted file holds both schemas (no
plaintext in it); `restore.sh` restored `game` (rows and Flyway version) from it and from a game-only
dump, removed tables left in the old `game` schema, and left the target's `auth` rows untouched.

🟡 **Not verified:** B2 itself (key capabilities, lifecycle rule, checksums through the B2 API), the
heartbeat service, the systemd units on a real VPS, and backup or restore against Supabase (network,
SSL, roles, size, time). Do a full drill before launch and record the measured restore time.

## 9. Logging, correlation and error monitoring

- Prod: ECS JSON on stdout (Docker rotates it). Each request gets `X-Request-Id` (client value
  accepted if well-formed); MDC `requestId`, `userId` (player id), and `gameId` for computer turns.
  Problem responses include the `requestId` so a player report maps to log lines.
- Never logged: tokens, emails, passwords, request bodies.
- Error monitoring: alert on `log.level = ERROR` (unexpected exceptions, computer-opponent failures,
  a full AI queue is WARN) in whatever log platform the operator uses. 🛠 No error tracker is
  integrated; adding one (e.g. Sentry) is a new dependency needing approval.
- Metrics endpoint is not exposed (only health). Adding Prometheus is future work.

## 10. Computer opponents in production

Two worker threads, one run per game at a time, at most 500 queued games (extra triggers are dropped
and picked up by the 15 s recovery sweep). On shutdown running turns get 10 s, then are interrupted;
progress is stored per action and the sweep resumes after restart. Watch for repeated
"Computer opponent failed" ERROR lines (a bug) and "queue is full" WARN lines (capacity).

## 11. Secrets management

- Secrets exist only in `.env.production` on the VPS (`chmod 600`, owned by the deploy user) and in
  GitHub Actions secrets if a deploy pipeline is added; none in the repository, image or frontend.
- The backend holds **no** Supabase secret or service-role key. The frontend holds only the
  publishable key.
- Rotate the DB password and SMTP credentials on staff changes; Supabase signing keys can be rotated
  in the dashboard (the API refetches the JWKS on an unknown `kid`).

## 12. CI/CD and rollback

Implemented: GitHub Actions `backend-ci.yml` (`./mvnw verify` with Testcontainers, Docker required)
and `frontend-ci.yml` (lint, tests, build).

Security checks (added 2026-11-13, product owner's request):

- `codeql.yml`: CodeQL code scanning, `security-extended` queries, Java and TypeScript from source,
  on every push and PR to `main` and weekly. Findings: Security → Code scanning.
- `dependency-review.yml`: a PR that adds a dependency with a known high or critical vulnerability
  fails.
- `.github/dependabot.yml`: weekly Maven and npm updates (minor/patch grouped), monthly GitHub Actions
  and Docker base images.
- 🛠 Repository settings (free on public repositories): enable Dependabot alerts and security updates,
  secret scanning with push protection, and require the CI and CodeQL checks on `main`.

Not implemented (deployment was not authorized):

1. On `main`: build the image, tag with the git SHA, push to GHCR.
2. Take a backup; deploy with `API_IMAGE=<sha> docker compose -f compose.prod.yaml up -d`; wait for
   the healthcheck; smoke-test `GET /api/v1/health` and a signed-in `GET /api/v1/me`.
3. Frontend: Cloudflare Pages builds `main` with the production `VITE_*` values.

**Rollback**: redeploy the previous SHA tag (schema stays — expand/contract); frontend: roll back
the Pages deployment. If a migration itself is wrong, fix forward with a new migration; restore from
backup only for data corruption.
